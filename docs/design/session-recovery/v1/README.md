## 产品决定

临时连接错误默认自动尝试恢复。提示在失败消息原位出现，复用现有错误组件的位置；不再同时在输入框上方显示同一错误。倒计时、进度、停止按钮始终可见，完整诊断与恢复记录默认折叠。

自动恢复以 **30 分钟的总时间窗口**为上限。等待基准为 **1s → 2s → 5s → 10s → 20s → 30s → 60s，之后维持 60s**，不再设置“最多 3 次”。在故障持续且请求很快失败的基准场景中约有 34 次自动尝试；真实次数会随连接耗时和服务冷却变化。宿主可加入小幅抖动，普通退避封顶 60 秒；`Retry-After` 可以要求更长的等待。当前原型的“持续失败”场景展示后期每分钟一次；“30 分钟到期”场景直接展示截止后的操作，不实际等待 30 分钟。

期限由首次可恢复错误建立：`deadlineAt = firstFailureAt + 30min`。退避、请求等待、网络离线、系统休眠都计入这 30 分钟。切换会话、renderer 重载、失败尝试、手动“立即重试”以及短暂收到 token 都不能重置期限。只有失败的模型请求完整成功才结束该恢复周期；用户到期后显式“重新开始”才建立新周期。

离线期间停止发请求；网络恢复时先核对 `deadlineAt`，未到期才检查原任务和恢复连接，到期则转入“自动恢复已到期”。renderer 的 `online` 只能作为提示。用户可以停止等待。应用重启后不自动执行历史任务，保留手动继续入口；renderer 重载、切换会话从主进程重新订阅。系统从休眠恢复时直接比较绝对期限，丢弃错过的 tick，只允许一次后续请求，不能补发积压重试。

正常状态下不常驻“已连接”标签。重连成功后，先核对任务进度，再继续；“已恢复，继续处理”显示 3 秒，随后折叠成一行可展开的“连接已恢复”。这里只表示连接和任务状态恢复，不表示任务完成。

## 故障分类

| 情况 | 自动处理 | 用户看到 / 可操作 |
| --- | --- | --- |
| 网络连接失败、连接重置、HTTP 408/502/503/504、可确认的临时 500 | 在安全边界内按 1/2/5/10/20/30/60 秒退避，最多持续 30 分钟 | “连接中断，正在自动恢复”；立即重试、停止恢复 |
| 429 限流 | 优先读取服务 `Retry-After`；无值时用退避策略 | “服务请求较多，X 秒后重试”；立即重试在服务强制等待期不可用 |
| 超长 `Retry-After` / 冷却超出预算 | 停止本周期自动恢复，保留可重试时间 | “服务暂时繁忙，请 X 秒后再试”；到时开放手动入口 |
| 主机网络离线 | 暂停自动请求，期限继续计时；联网且未到期时核对原任务 | “网络已断开，等待网络恢复”；检查连接、停止等待 |
| 401/403、无效密钥 | 不自动重试 | “模型密钥已失效”或对应验证原因；检查模型设置 |
| 明确余额/额度耗尽（含返回 429 的此类错误） | 不自动重试 | 检查额度、更换模型；优先级高于一般限流 |
| 请求参数错误、模型不支持输入、上下文上限 | 不自动重试 | 明确配置/输入原因及对应修复入口 |
| 用户停止、权限拒绝、预算限制、工作区不可用 | 取消恢复计划；需要时先修复条件 | 显示停止或具体原因，不能改写成网络失败 |
| 工具请求已发出，回执丢失 / 部分提交状态未知 | 连接可以恢复，任务暂停；只允许查询结果 | “连接已恢复，需要核对操作结果”；核对操作结果、暂不继续 |
| 其他无法分类的错误 | 不猜测为临时网络错误 | 保留手动重试和详情 |

上述分类应基于结构化 `status/code/cause/providerResponse`。现有文案正则只用于旧记录兼容，不能承担自动执行策略。除明确可恢复的错误外，不将所有 5xx 或异常文本一概判为可恢复。

**截止行为：**到 30 分钟后不再发起新的自动请求；还在等待连接/首个响应的请求按剩余期限取消，已正常生成内容的健康流可以按正常流程完成，不能仅因重试期限到达就打断有效回复。若这个流再次失败且已到期，转交用户。等待基准不包含请求本身耗时，每次失败后才排下一次；连接/首响应等待上限建议 15 秒，并服从剩余期限。正常长回复仍使用流停滞检测。

429 优先遵守 `Retry-After`，不能被“立即重试”或退避封顶绕过。如果服务允许的最早重试时间或下一次退避落在截止时间之后，只等待到截止时间并结束本周期。截止前没有足够时间完成下一次连接时也不强行发出。旧的 3 次 / 60 秒策略须从所有相关层级移除，所有真实请求仍计入现有 run 的总请求与费用预算；若先触及明确的预算限制，提示该原因并停止，不能误报成网络失败或偷偷重置预算。

## 恢复边界：先恢复通路，再决定能否继续任务

1. **仅连接/订阅丢失，宿主原任务仍运行：**重新订阅并拉取快照、按事件游标补齐；不发送新的用户输入。云端状态未知时文案为“正在检查原任务”，不能声称任务已失败或已暂停。
2. **模型请求失败，但尚未发出任何工具操作：**保持当前逻辑输入与附件，只重试失败的模型请求。若已显示部分文本，将失败的部分保留为一次未完成输出，新结果显式替换该部分；不拼接两段独立生成文本，也不重复创建用户消息。
3. **已有完成的工具步骤，且会话可恢复：**从最近已持久化的 session entries / tool results 继续失败的模型请求；显示核对进度。只在能够确认工具结果完整、没有未决副作用且恢复 API 已验证时开启。
4. **工具执行中或结果未知：**暂停后续任务。先以只读方式查询执行结果；查明已完成则记录结果，确认未执行才允许重新发出；无法查明时明确告知并交由用户选择。不能把“重新连接”按钮接成重发命令。
5. **会话不可恢复 / 缺少可信检查点：**保留文本、附件、工具记录与草稿，提示“当前进度已保留，需要手动继续”。不自动调用旧 `handleRetryTurn` 重跑整轮。

“当前进度已保留”表示现有记录未丢失；“恢复后继续”只用于恢复资格已确认的任务。当前主预览使用已确认工具读取完成、会话可恢复的样本；不能将这个文案无条件套给所有失败。

## 状态与组件

状态流：`failure → classify → waiting / offline / needs-action → connecting → reconciling → resumed`。重试失败回到 `waiting`，30 分钟到期则 `exhausted`。任何在途自动状态都能进入 `stopped`；结果未知进入 `needs-verification`，核对失败时留在此态，不能直接继续。

- **恢复消息 `RecoveryNotice`：**14px 线图标，13px 常规字重状态，12px 计数；使用 Hemi 现有 `tokens.css`。默认无边框、无独立卡片底色，一行 40px 高；等待/恢复中用状态绿小图标，需处理时用局部警示色。每行最多一个文字操作和详情箭头；展开内容以左侧细线关联。
- **倒计时：**一行展示下次重试倒计时；累计尝试次数、已持续时长和剩余窗口放入详情。由 `nextRetryAt` 推导，后台节流后不积压触发多次。读屏只播报状态转移，不每秒播报时间。
- **正在连接：**显示“第 X 次”，取消“立即重试”入口，只留停止，防止双请求。
- **离线：**不放持续旋转的等待图标。一行显示“等待网络恢复”和停止入口；检查连接放入展开详情。
- **恢复记录：**原始失败原因、每次请求时间和结果、停止原因；默认折叠，去除密钥、token、用户正文等敏感内容。恢复历史按一次恢复周期分组，不能每次重试生成新的错误气泡。
- **输入区：**当前草稿、附件和引用保持可编辑。首版恢复期间不允许新消息插入原恢复任务，提供“停止恢复后发送”。选择停止会先由宿主确认取消，再开放新消息发送。已有排队输入暂停自动推进；恢复成功按原队列继续，终止恢复则交用户恢复队列。
- **会话列表：**离开当前对话不停止恢复。沿用现有状态位显示“恢复中”；恢复耗尽或需用户处理才用现有未读提示，不新增全局通知系统。

只新增局部反馈，正常对话、语音通话、模型切换入口保持现有结构。当前交互稿中的模型设置与操作查询弹层仅验证返回路径，不作为真实设置页的视觉改版。

## 宿主实现建议

自动恢复由主进程持有，renderer 只渲染状态、发送用户意图。建议在 `agent-runtime` 中增加一个恢复协调器，接在模型请求失败的可恢复边界；连接/订阅与模型请求用不同分类，同一任务只有一个恢复 owner。

建议持久化 `recoveryId/conversationId/runId/requestId/generation/phase/attempt/firstFailureAt/deadlineAt/nextRetryAt/errorCategory/checkpointRef/lastEventCursor`。事件与快照携带单调 revision。renderer 重载或切回会话读取权威状态，过期事件不能覆盖新状态。

- 原子领取 attempt：立即重试、到时触发、网络恢复触发共享去重锁；每个逻辑请求最多一条在途链。手动“立即重试”只提前当前排期，沿用同一期限和尝试计数；仍须遵守服务冷却及最小间隔。到期后的“重新开始”是显式建立新周期。
- “停止恢复”先失效 generation、取消定时器与 AbortController，再确认取消；所有晚到的连接成功和 token 都按 generation 丢弃。用户停止不能被 SDK 自动重试重新拉起。
- 重试策略只能有一个所有者。审计 `pi-chat`、SDK、provider、自动路由与宿主边界，关闭或显式计入内层重试；既有模型候选切换计入同一总预算。首版不自动更换用户选定模型。
- 不修改已完成/不确定操作的 `toolCallId`。新网络请求可以有新的 request id，但保持逻辑 run、input 和恢复链关联。**客户端去重不等于服务端操作恰好执行一次**；副作用工具必须有可验证结果或幂等键才能自动重发。
- 模型设置改变不直接修改正在恢复的请求快照。用户显式选“使用此配置继续”时，先取消旧恢复链，再重新校验能力/附件/权限/预算，建立新的恢复 generation。
- 恢复不隐式同意权限、扩大工作区或重新发送外部操作。已有授权仍按原任务范围使用；身份、工作区或执行主体变化需要重新评估原恢复资格。

建议分阶段落地：先做结构化错误和宿主可见退避，覆盖请求尚未发出工具的场景；再做 session checkpoint 恢复与事件补齐；最后按工具逐个接入结果查询。第二、三阶段就绪之前，不能提前对中途执行失败承诺自动继续。

## 验收要点与交付

设计交付：可操作局部预览、六个状态组件、设置与结果核对的返回路径、导出截图。验证脚本 `verify.mjs` 渲染并检查此原型，不代表生产恢复能力已验收。

落地后的验证必须覆盖：503→自动成功；连续失败→逐级退避至每分钟一次→30 分钟到期；429 冷却；401/额度→直接修复；离线→联网；休眠跨过期限；重载/切换/手动重试不重置期限；Retry-After 跨过截止；停止与晚到回包竞争；连点和多窗口只发一次；切换会话/renderer 重载恢复；应用重启不自动重跑；部分文字不拼接；已完成工具不重做；未决操作只查询；草稿/附件/队列保留；SDK 与路由没有叠加重试。IPC/服务变更需沿实际 renderer→IPC→宿主→本地受控 provider→持久化状态链检查；UI 生命周期变更在 Vite 与 built renderer 各验证一次，并记录提交、环境、命令、差异和剩余限制。

设计交付阶段没有运行产品全量测试或外部模型；后续生产实现的验证记录见上方技术文档。

设计策略样例由 `recovery-policy.mjs` 提供。验证脚本用虚拟时间覆盖整个 30 分钟窗口和边界，不实际等待 30 分钟；该模块仅用于原型，尚未接入生产。
