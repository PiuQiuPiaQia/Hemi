## 1. 问题与目标

主 Agent、子 Agent 和后台进程分别有执行、等待、额度、超时、取消和持久化逻辑。每一层单独处理的结果，不一定能形成正确的整体行为：任务可能互相等待；任务仍在执行但界面没有反馈；已经结束的工作仍占用运行状态；已发生副作用的动作在恢复时被再次执行。

本次实际故障发生在前台子任务：主 Agent 同步等待子任务；主子共享的分段请求额度触顶后，子任务等待父级推进下一段；父级推进又要求前台工具已经返回。双方等待，所有模型请求及命令已结束，目标仍显示运行中。已有“子任务触顶唤醒父调度”测试使用后台派单，没有覆盖这条前台路径。

用户进一步提出：没有输出不等于卡死；仍在正常推进的长任务可能超过预设时间；到限时由谁判断、依据什么继续或停止；报错、无法清理、父级不可用、重启等意外情况如何反馈。因此，本需求不能只解决这一次死锁，也不能把所有未知情况归结为“等到一个固定时间后杀掉”。

目标是：正常工作有可解释的等待与继续路径，异常工作有可执行的处理路径，无法确认的工作有明确的不确定性与接手方式；任何恢复、重构和兜底不得丢失历史上已经建立的归属、取消、结果保存与副作用保护。

## 2. 范围与评审边界

本需求约束可观察行为，不预先选择新的调度框架、数据库、看门狗数量或默认时间。复用现有账本、Pi 会话、进程守护及客户端投影的可行性应优先核对。

前两轮讨论中的“60 次改软复盘”“前台等待约 10 秒后返回任务编号”“静默只更新界面”“子任务用完额度后先等自己的进程”“硬截止时直接停止”等，均是待重新评审的候选处理方式。用户已指出它们没有充分覆盖正常和异常边界，不能据此直接实施。

本轮与 CC 继续核对反例后的具体建议见[生命周期候选方案](agent-task-lifecycle-proposal.md)。其中推荐选择和验证探针供 review 使用，不关闭本需求的 D 项，也不代表运行时已经修复。

不在本次范围内：生产部署、自动重跑用户的历史目标、修改已有用户数据、重新设计聊天界面、将工作流节点改成另一套聊天目标，以及重写整个持久化系统。工作流复用的执行边界仍需纳入回归，但其节点调度契约独立保留。

## 3. 术语与判断依据

| 概念 | 含义与约束 |
| --- | --- |
| 目标 | 一次已受理的用户意图及明确续接；不等于一次模型生成或一次工具调用 |
| Agent 执行 | 主或子 Agent 的一次受管理执行；可涉及模型请求、工具与后台工作 |
| 后台工作 | 已受理、可识别归属、可查询和取消的命令或任务；转后台不产生新的目标 |
| 前台等待期限 | 调用者愿意同步等待多久；到限本身不证明工作失败，也不授权停止工作 |
| 静默／观察阈值 | 多久没有可见输出或需要核验状态；不能直接等同执行硬截止 |
| 执行硬截止 | 经适用策略或明确授权形成的执行边界；来源、范围和到期动作必须可核对，不能自动续期 |
| 恢复窗口 | 对失败请求进行恢复的允许时间；与健康流、整个目标和命令执行的时间分别管理 |
| 硬预算 | 真实请求、费用等资源的约束；耗尽不能靠隐藏检查、备用切换或总结请求绕过 |
| 存活 | 进程存在、连接心跳或宿主仍响应；不证明操作正在推进 |
| 输出活动 | 模型增量、日志或输出字节增加；不单独证明用户目标有进展 |
| 可核对进展 | 与目标有关的结果、已完成操作、产物或检查事实；判定方法及无进展策略见 D-05 |
| 结果未知 | 已经发起的操作可能发生了副作用，但结束、保存或清理未能确认；不得伪装为成功、未执行或已停止 |

## 5. 行为需求

### R-01 目标与任务归属

主、子 Agent、命令、工具执行、等待及报告均须关联真实目标与执行代次。转后台、调度分段、重载或结果送达不能改变归属或创建替代目标。短显示编号不能代替持久任务身份。每个仍在执行的操作都必须有负责其结果收集和清理的宿主。

### R-02 消除循环等待

执行者不得等待一个必须由“正在等待自己的祖先结束当前回合”才能解除的条件。至少覆盖前台／后台子任务、额度触顶、并发准入、资源等待与结果保存。不能靠放宽完成检查、丢弃未结束工具、伪造 SDK 返回或重派副作用消除表面忙碌状态。

### R-03 调用返回与实际结束分离

前台等待、结果读取或界面请求到限，只影响该次等待，不自动取消真实任务。若采用让渡，工具必须真实返回可识别的受理结果，后续结果仍有可靠接收方；主 Agent 暂时没有文字输出不等于整个目标已完成。是否采用约 10 秒等候值见 D-01。

### R-04 等待原因与状态可解释

每个活动或等待状态须能指出实际执行／依赖对象、起点、解除事件、负责者和适用约束。主 Agent 没有模型请求但明确在等子任务，应显示该等待；没有请求、工具、依赖和可解释等待依据时，应进入异常核对或未确认状态，不能无限宣称正常运行。界面展示状态不作为继续执行的授权。

根调度须覆盖已停止推理的后代仍持有的必要工作，不能只等待尚未结算的子 Agent 或根会话自己的命令。正常等待后代工作的路径须先于完成校验；保留校验对未结束工作的拒绝，不能让缺少调度等待被误作目标执行失败。

### R-05 正常长任务与截止分类

正常工作不得仅因没有文字输出、前台等待到限、软复盘点或模型暂时停止生成而被判失败、取消或重新执行。必须区分观察阈值、调用者等待、请求超时、命令硬截止、恢复窗口、硬预算与用户明确的停止／截止要求。

每项约束须保存来源、适用对象、默认或显式设置、绝对期限、允许修改者和到期动作。用户明确停止、真实硬授权边界或硬预算不得被模型自行延长。正常工作到默认执行时限时究竟停止、核验后继续还是请求选择，尚未定案，必须关闭 D-02／D-03 后才能实施；不能把此前“所有到期都杀”的候选策略写成已批准行为。

现有命令的 timeout_ms 在实际执行中仍是硬截止；它来自工程默认或模型参数，不意味着已受理后可以自行改为软提示。将来若改变分类或允许续期，必须显式改变相应契约，保留原承诺与授权记录。休眠、离线、时钟跳变是否计入各类期限分别按 D-11 决定，不把模型恢复窗口的规则直接推广到所有任务。

### R-06 静默、存活与进展分别处理

没有输出只能说明缺少可见输出；日志刷屏、心跳或 CPU 活动也不能单独证明目标在推进。系统须保留可查询的真实状态并标明进展未确认。静默观察、业务无进展、模型流中断和进程失联必须有不同依据及处理路径。

已有有界静默核验能力的保留或替代需按 H-02 评审。任何核验都须限定归属、次数／资源和副作用；不能通过模型轮询、占位命令或重复启动任务维持“有活动”。核验触发者、升级条件、无法核验时的兜底见 D-04／D-05，不能默认为新增或取消某种自动检查。

日志持续输出会推迟现有基于 lastOutputAt 的静默检查；因此该机制不能覆盖日志循环。若采用启动时声明的检查点，输出不能推迟该检查点。现有 noProgressRounds 在仍有待结束工作时不会执行，也不能作为这些场景的兜底。

### R-07 预算、复盘与控制反馈

调度分段与硬资源预算须分别表达；调整分段不得迫使必要工作等待祖先放行。实际 HTTP 尝试及其用量按真实发生记录，重试、备用、压缩、校验和总结须有可核对的用途与预算归属，不能形成额度外的隐式无限循环。

硬预算耗尽后，不得依赖一次必定成功的新模型请求来停止工作、保存状态或提供基础反馈。对在途请求、已受理进程、尚未消费结果及剩余事项须有明确处置，不能直接丢弃或误报完成。软复盘、总预算、独立子任务限额及预留收尾能力仍须按 D-06 评审。

拒绝第 N+1 次请求、目标整体终止、单项工作的硬截止是不同事件。额度准入关闭本身不等于已经在途的第 N 次请求或已受理工作被取消；若总额度政策要求结束目标，须显式进入目标终止流程，保留其原因、范围和清理结果。现有总预算收口会清理目标树，是否改变按 D-06 决定。独立子任务限额可用于公平分配，但不是消除循环等待的必要条件。

### R-08 错误与请求恢复

区分可恢复的模型网络故障、鉴权／额度／输入错误、工具执行错误、结果未知、持久化失败和清理失败。工具报错须带真实结果返回负责决策的 Agent；操作失败不自动证明整个目标无法继续，操作成功也不证明目标完成。

请求恢复只针对适用的失败请求，不重新提交整条用户目标或重做已完成工具。不得叠加 SDK、供应商与宿主恢复窗口。重试与备用须遵守冻结策略、同一绝对恢复期限、取消与预算；健康流跨过某个恢复期限时沿用既有已验证规则，不得仅因恢复时钟到点误杀。错误未知时先保存事实并限制不确定副作用的重试。

### R-09 后台进程与子任务的生命周期

覆盖启动、归属登记、执行、进程退出、输出排空、结果保存、报告投递及清理确认。进程退出但 socket／输出管道未关闭，不能让整个目标无限等待；工作已经完成但进程仍挂起，也不能仅凭进程存活视为仍有必要工作。

子 Agent 崩溃、预算耗尽或结束推理后，其仍在执行的命令必须继续有明确宿主管理者。子任务报告、Agent 是否仍推理、进程是否结束是独立事实，不得假设它们同步结束。是否等待、保留、取消或转交剩余进程，以及谁有读取／取消权限，按 D-07 评审，不得留下不可访问的进程，也不能为让报告返回就误停必要工作。

报告可读与目标完成也须分别记录。仍有可能改变文件或产物的工作时，报告须注明截点和未结束工作，不能把一次子 Agent 结算时的文件快照当作最终成果。会话淘汰、工作流释放及 dispose 路径均须遵守已决的工作归属规则；只删除 modelError 时的 abort 不能构成完整修复。

### R-10 取消、隔离与清理未知

用户停止及目标失效优先于重试、让渡、复盘、结果唤醒和完成校验。须区分单条工作停止与整个目标取消。停止受理、停止执行和确认清理是不同事实；有界处理结束仍无法确认时，明确说明执行结果／清理未知并保持必要隔离，不能永久无反馈或假成功。

不得强占未知是否仍生效的资源租约。隔离范围须与实际不确定归属／冲突能力相符，不能随意封锁无关会话。独立常驻服务仍按明确授权和系统服务生命周期管理，不从后台标志、Shell 脱离或无限续期推导出服务授权。

### R-11 结果可靠送达与持久化失败

结果保存、通知和消费须按稳定身份去重，取消一个等待者不能消耗其他处理者的结果。多个结果同时到达可合并处理，但每个结果仍可核对。前台返回与后台投递若允许切换，切换和任务完成恰好同时发生时，也必须有且仅有一条有效交付路径；不能两边都未交付或两边重复处理。旧目标、旧代次和已取消执行的迟到结果不得唤醒新任务。

持久化健康时沿用先保存再确认消费。保存失败时必须保留执行已结束／可能已生效的栅栏，向等待方和界面报告保存未确认，限制自动派发；不能为等写盘而无限占用忙碌槽，也不能声称数据必然已落盘。补存只补状态，不调用模型、不重放工具、不自动恢复队列。存储持续不可用直至进程退出时的数据缺口须如实说明。

“已保存结果”不等于“已交付主 Agent”。确认消费前，须核对相应 eventId 已写入并保存到实际 SDK 上下文锚点；预览、临时领取或工具处理器准备返回都不算确认。交付失败可按 eventId 重投或补确认，不重执行业务。旧目标的事件标为 obsolete 只取消模型唤醒资格，不能删除已经保存的结果。

### R-12 收口、人工接手与恢复

模型生成结束、子任务报告、命令退出码 0 均不能单独证明整个目标完成。保留现有严格完成校验，未确认工作及报告须按其原契约处理。部分完成、外部受阻、等待用户、失败、取消、保存未确认和清理未知须可区分，并保留可确认成果、未完成事项及下一步。

需要用户登录、验证码、选择或授权时给出实际可回答的问题并挂起；保留必要页面与上下文，不假称完成或自动操作。renderer 重载／客户端重连不等于宿主重启；宿主重启只核对、回收已知归属并标记中断／未知，不自动重放副作用。父 Agent 或宿主不可用时的报告持有者、退出保护和用户接手见 D-08。

### R-13 展示与诊断

默认一行真实状态，展开只显示最近输出和停止入口；不新增倒计时面板或为解释实现而增加用户操作。至少能区分等待对象、暂无新输出、正在恢复、等待答复、部分完成、执行错误和状态未确认。没有业务进展依据时不生成百分比或正常保证。

诊断保留执行／父子身份、最近确认事实、等待原因、约束来源、截止、停止原因、请求用途、结果消费和清理／保存状态。真实错误应可追溯；凭据、个人对话、设备身份及连接秘密不得进入需求、测试产物或提交。仅靠同一主进程的定时器不能保证检测该进程自身完全停摆，能力边界必须披露。

### 判断责任

| 主体 | 可负责的判断 | 不能据此推导的结论 |
| --- | --- | --- |
| 宿主程序 | 真实执行身份、请求和进程事件、退出码、约束到达、取消、保存及清理结果；明确规则下可核对的产物证据 | 进程存在、日志增加或退出 0 本身不证明用户目标完成；同进程计时器不保证检测自身完全停摆 |
| 主／子 Agent 与完成校验 | 在已有授权及预算内解释错误、核对目标进展、决定下一步、提出接手问题；语义判断须有实际证据 | 不能自行更改用户硬约束、伪造底层状态、把未知操作当作未执行而重放 |
| 用户 | 明确目标与修正、停止、人工操作，以及对需要新授权或未决策略的选择 | 用户未答复不代表同意延长、增加预算或自动执行待核对输入 |

## 8. 验证与 review 要求

1. 需求 review 先逐项确认 H、R、S 和 D；未关闭的 D 项须保持未决，实施方案不可自行选择默认答案。
2. 技术方案须提供“旧保证 → 新负责模块 → 状态／事件 → 验证场景”的对应表，并明确哪些旧入口被移除及替代路径。
3. 实现验收使用真实共享核心、Pi SDK、Host／IPC、账本、文件系统和受管进程；外部模型 HTTP 可用受控响应及故障时序代替。持久化和平台清理应在拥有该行为的实际边界验证，必要故障注入不能被写成真实外部故障实测。
4. 至少覆盖前台／后台子任务 × 无／有子属进程 × 按 D-06 决定后实际存在的预算边界，以及 S-01 至 S-31。旧共享分段路径须保留故障复现或替代后的等价验证；删除一种预算机制不能跳过其曾触发的循环等待检查。并发数和重复次数不是验收目标本身，测试应对准状态、身份、执行次数和迟到副作用。
5. UI 生命周期变更在 Vite 开发 renderer 和构建 renderer 各验证；Windows Job、远端 SSH 和实体移动能力分别记录环境及缺口，不能用 macOS fixture 代替。
6. 使用新的 HEMI_USER_DATA_DIR，隔离于安装版数据；记录基线、命令、平台、实际经过的边界和未覆盖项。未经用户授权不更新生产服务或设备。
7. 本次需求整理只检查文档内容、引用及差异；历史测试结果与本次验证分开，不因写入需求文档就标记运行时问题已解决。
