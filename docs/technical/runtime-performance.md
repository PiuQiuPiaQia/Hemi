# 任务输出与长会话性能

本次处理任务输出、多任务运行和长会话翻阅时的主线程阻塞与展示数据驻留。历史档案继续完整保存；展示层回收不会剪除模型上下文或删除历史 QA。

## 运行事实库

`run-journal.mjs` 保持原有受理、结算和恢复接口，存储由整库 JSON 改为工作线程中的 SQLite 增量事务：

- `journal-draft.mjs` 共享未改动记录，只复制本次编辑的记录。事务成功才应用到内存；受理失败不进入内存或重试队列，已确认的终态在写失败时继续阻止重复执行并等待补存。
- `journal-storage-worker.mjs` 使用 Node 内置 SQLite；`records(kind,id,value)` 保存各记录，`metadata` 保存版本和修订号。每次写入在事务中校验预期修订号，防止不同写入器互相覆盖。
- 一个共享工作线程串行处理存储工作；请求在途时保持进程存活，空闲时 `unref`。数据库每次操作后关闭，使用 `synchronous=FULL` 和默认回滚日志模式。
- 查询使用限定表、会话、根任务的 `snapshot(options)`，或先投影再复制结果的 `project(fn)`，避免只读一条记录却复制整个事实库。事实库的完整内存索引仍保留。

首次读取时，将旧 `runtime-v2/run-journal.json` 导入临时数据库，成功关闭后原子安装 `run-journal.sqlite`；导入失败不会安装半成品，旧 JSON 保留。后续写入以 SQLite 为准，旧 JSON 仅在显式导出时更新。离线诊断脚本通过 `journal-inspection.mjs` 读取，兼容旧 JSON 和新数据库。

备份仍使用便携 JSON：打包前通过一致读事务导出，避免复制正在使用的数据库。恢复比较也使用导出快照；备份 JSON 胜出时，被替换数据库进入安全副本，重启后从恢复的 JSON 重新导入。需要回退到只认识 JSON 的旧版本时，应先由新版导出最新事实库，不能直接把保留的旧 JSON 当成当前状态。

## 会话保存与用量

`atomic-json-store.mjs` 将读取、JSON 解析、序列化和临时文件写入交给工作线程。主线程只在一个没有 `await` 的短临界段比较文件指纹并原子替换：原有同步档案写入若穿插进来，会丢弃旧准备结果并根据最新档案重算，保留 turns、agentSession、flow 等兄弟字段。持续冲突会失败并进入现有存储错误处理，不静默覆盖。

`flow-store.mjs` 按会话串行提交；成功后只移除已经提交的那批变更，后到变更仍在队列。失败保留队列并重试。模型调用的用量一次批量入账，会话用量通知按 32 ms 合并，减少反复读写同一份大档案。部分低频同步档案写入仍保留。

## 展示窗口与回收

- 桌面本地 IPC 复用共享 `flow-window.mjs`：默认最近窗口目标为 32 行、256 KiB，QA 分组最多 100 行；单条超大消息允许超过字节目标。向上翻阅时按页读取。
- 打开、恢复本地会话使用 `windowed` 元数据接口，只返回会话身份、标题、时间、模型组、工作区和剪除键等展示字段。完整 flow 从分页接口读取，防止原始档案或旧会话载荷重复驻留页面。
- `history-view.ts` 正常向上翻阅时以 256 行、2 MiB 为回收目标，保留新读入的页及实时末尾，移除的中间区域显示可重新加载的间隙。单页、单条超大消息及用户显式加载间隙时允许超过目标；返回实时末尾释放回载的历史。无关终态 run/task/artifact 元数据一同释放。
- DOM 虚拟列表继续保留编辑、焦点和文本选择涉及的行；存在这些交互时不因跟随末尾回收历史。ResizeObserver 测量通过 requestAnimationFrame 合并。
- 切换会话时释放客户端副本、历史、订阅及本地实例缓存；视图租约区分新旧订阅，迟到的旧清理不会释放新订阅。
- 主进程闲置控制器 LRU 软上限为 8 个，淘汰前先排空写入。正在查看、运行中、待回复、排队输入、待处理汇报、后台命令及未清理任务保持驻留，因此不是硬内存上限。
- 旧消息展示转换使用弱引用缓存，回收的消息不会被缓存持续持有。完整回答复制按 run 和 generation 从宿主按需取全文，避免分页后只复制当前片段。

### 同机合成基准

对比已安装 v0.2.45 的模块与本次实现，均操作临时合成数据：事实库 44,483,761 字节，会话档案 17,412,989 字节。以下为单次样本，不能当作全部生产负载的保证。

| 场景 | 原实现耗时 | 优化后耗时 | 原最大主循环延迟 | 优化后最大主循环延迟 |
| --- | ---: | ---: | ---: | ---: |
| 工具开始、结束两次写入 | 174.8 ms | 1.2 ms | 72.8 ms | 0.7 ms |
| 会话范围查询 | 33.7 ms | 2.6 ms | 33.8 ms | 1.1 ms |
| 46 条用量入账 | 3493.2 ms | 96.0 ms | 3492.8 ms | 3.9 ms |

四任务并行输出并执行实际保存时，开发版输入操作 52.2 ms、构建版 27.5 ms；150 个 rAF 间隔样本的 P95 分别为 17.2 ms、17.5 ms，最大为 17.6 ms、17.8 ms。rAF 间隔表示回调节奏，不等同于 GPU 实际呈现帧率。原始报告和截图由脚本输出到 `.visual/workflow/runtime-performance/`。

发布准备时，Windows CI 暴露了旧交接测试固定 200 ms 释放子进程的竞争：较慢的持久化可能尚未到达交接点，进程就已退出。测试改为在真实挂起边界释放并等待终态，同时避免清理期间重新创建悬空等待；继续验证完成事件只交付一次，以及取消后不推进或重启目标。

存储故障测试通过 `prepareExecution` 等待运行时启动恢复完成后再注入故障，避免把初始化失败误当作终态保存失败；异常路径也会关闭临时 HTTP 服务。直接写入用量事实的测试同样先等待启动恢复。

备份恢复夹具明确设置备份比本地文件更新，不依赖操作是否在同一秒完成；24 轮历史读取和后台命令集成场景使用覆盖慢盘的总体测试时限，保留生产命令的原有截止时间和所有结果断言。相关 36 项本地集成测试通过，Windows 独立验证 35 项通过、1 项按已有平台条件跳过。

以上是实现阶段的验证记录，正式版本的双平台门禁与产物结果以对应 Release CI 为准。没有替换本机安装包、部署生产 Bot 或更新物理移动设备；实际外部模型长时间负载、安装升级、Windows 桌面交互和物理移动端仍需分别验证。事实库索引和受保护的活跃控制器仍驻留内存，本次回收范围是展示数据与闲置控制器。
